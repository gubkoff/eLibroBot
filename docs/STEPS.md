# Пошаговый разбор плана eLibroCargoReportBot

Документ для пошаговой реализации бота **eLibroCargoReportBot**. Каждый шаг можно разбирать отдельно и переходить к следующему после выполнения.

**Чёткий чеклист по подшагам:** [TASK_BREAKDOWN.md](TASK_BREAKDOWN.md).  
**Роадмап для отметки этапов и обсуждения:** [ROADMAP.md](ROADMAP.md).

---

## Шаг 1: Скелет проекта

**Цель:** поднять бота, чтобы он запускался и отвечал на `/start`.

**Что сделать:**

| Действие | Детали |
|----------|--------|
| Создать `requirements.txt` | **aiogram** >= 3.x, `pydantic-settings`, загрузка из `.env` |
| Создать `.env.example` | Переменные: `BOT_TOKEN`, `SOURCE_GROUP_ID`, `TARGET_GROUP_ID` (значения-заглушки) |
| Создать `config.py` | Класс настроек на `pydantic-settings`, чтение из `.env` |
| Создать `main.py` | Инициализация бота на **aiogram** (eLibroCargoReportBot), хендлер `/start` с приветствием с именем бота, запуск через `dp.start_polling()` (или эквивалент для aiogram 3) |
| Добавить в `.gitignore` | `.env`, `__pycache__`, `*.pyc`, **`venv/`**, `.venv/` |
| Создать и использовать **venv** | В корне проекта: `python -m venv venv`, активация, затем `pip install -r requirements.txt`. Запуск бота только из активированного venv. |

**Результат:** по команде `python main.py` бот стартует и на `/start` отвечает приветствием (в ЛС или в группе).

**Вопросы для обсуждения:** только long polling или сразу заложить возможность webhook; нужен ли логгер в консоль/файл с первого шага.

## Шаг 2: Парсер

**Цель:** из текста сообщения получать список структурированных записей `Record`.

**Что сделать:**

| Действие | Детали |
|----------|--------|
| Создать `parser/models.py` | Dataclass `Record`: `date`, `amount` (Decimal), `category`, опционально `raw_text` |
| Создать `parser/parser.py` | Функция `parse_message(text: str) -> list[Record]`: разбивка по строкам, разбор формата «дата сумма категория» (разделители пробел/запятая/табуляция), приведение типов, пропуск невалидных строк |
| Определить формат даты | Например `DD.MM.YYYY` или `YYYY-MM-DD` — один основной формат в первой версии |
| Логирование | При пропуске строки — `logging.debug` или `warning` с текстом строки |
| Тесты (опционально) | `tests/test_parser.py`: несколько строк с валидными/невалидными данными → проверка длины списка и полей `Record` |

**Результат:** вызов `parse_message("2025-02-26 100 продукты")` возвращает список из одной записи с полями date, amount=100, category="продукты".

**Вопросы для обсуждения:** один формат строки или несколько (например ещё таблица); как обрабатывать строки без категории (подставлять "без категории" или пропускать).

## Шаг 3: Калькулятор

**Цель:** по списку `Record` считать агрегаты для отчёта.

**Что сделать:**

| Действие | Детали |
|----------|--------|
| Создать `report/calculator.py` | Функция `calculate(records: list[Record])` → структура с полями: `total`, `by_category` (dict), при необходимости `by_period` (день/неделя/месяц) |
| Тип результата | Dataclass или TypedDict, который потом принимает `pdf_builder` |
| Пустой список | Вернуть нулевые/пустые агрегаты, не падать |
| Тесты (опционально) | Несколько записей → проверка `total` и `by_category` |

**Результат:** вызов `calculate([Record(...), Record(...)])` возвращает объект с общей суммой и разбивкой по категориям.

**Вопросы для обсуждения:** нужна ли разбивка по периодам в первой версии или достаточно общей суммы и по категориям.

## Шаг 4: Генерация PDF

**Цель:** по результатам калькулятора сформировать PDF и сохранить во временный файл.

**Что сделать:**

| Действие | Детали |
|----------|--------|
| Добавить в `requirements.txt` | `reportlab` |
| Создать `report/pdf_builder.py` | Функция `build_pdf(data: WeighingPrintData) -> Path`: заголовок, дата отчёта, реквизиты, таблица позиций, итоги, сохранение в `tempfile.NamedTemporaryFile(delete=False, suffix='.pdf')`, вернуть путь |
| Подпись в PDF | Например «Сгенерировано: {дата/время}» внизу страницы |
| Закрытие файла | После записи PDF закрыть файл, чтобы его можно было открыть для отправки |

**Результат:** вызов `build_pdf(data)` возвращает путь к временному PDF-файлу, готовому к отправке.

**Вопросы для обсуждения:** нужен ли логотип/брендинг; одна страница или разбивка на несколько при большом числе записей.

## Шаг 5: Хендлер сообщений и пайплайн

**Цель:** связать всё в один пайплайн по входящему сообщению из группы-источника.

**Что сделать:**

| Действие | Детали |
|----------|--------|
| Создать `bot/filters.py` | Фильтр: чат — группа с `chat_id == settings.SOURCE_GROUP_ID`, сообщение с `message.text` (не пустое); опционально `from_user.id in ALLOWED_USER_IDS` |
| Создать `bot/handlers.py` | Один хендлер на сообщение: 1) парсинг `parse_message(message.text)`, 2) если данные не извлечены — выйти (или отправить «Нет данных» в группу-источник), 3) создать `WeighingPrintData` и вызвать `build_pdf(data)`, 4) отправка PDF в целевую группу через **aiogram** (`message.bot.send_document(chat_id=TARGET_GROUP_ID, document=...)`), 5) удалить временный файл `os.remove(pdf_path)` |
| Обработка ошибок | try/except вокруг пайплайна: логировать, при необходимости отправить в группу-источник короткое сообщение об ошибке |
| Подключить в `main.py` | Зарегистрировать хендлер с фильтром по группе-источнику; команду `/start` оставить отдельно (все чаты или только ЛС). Использовать **aiogram** (Router, filters, Bot). |

**Результат:** при отправке структурированного сообщения в группу-источник в группу-получатель уходит PDF-отчёт по данным из этого сообщения.

**Вопросы для обсуждения:** при пустом парсинге — молча пропускать или писать в группу «Не удалось извлечь данные»; при ошибке генерации/отправки — куда слать уведомление (источник/админ).
