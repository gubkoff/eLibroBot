# Черновик бизнес-правил (план V3)

Статус: **черновик**, отражает текущий код до рефакторинга.

---

## 1. Сумма (`amount`) — правило из `parser/parser.py` (стр. ~150–156)

**Файл:** `parser/parser.py`

1. Из сообщения парсятся:
   - `price_per_ton` (или `0`, если нет / не распарсилось),
   - `amount` из полей суммы (или `0`),
   - `netto_kg`, `adjusted_netto_kg` (целые кг; при отсутствии корректировки `adjusted_netto_kg` в модели сейчас `0`).

2. Вес для расчёта суммы (кг):
   ```text
   weight_for_amount_kg = adjusted_netto_kg or netto_kg
   ```
   (при ненулевой корректировке берётся она, иначе нетто.)

3. **Пересчёт суммы** (перетирает значение из сообщения), если одновременно:
   - `price_per_ton` **истинно** (не `0`),
   - `weight_for_amount_kg` **истинно** (не `0`).

   Тогда:
   ```text
   amount = (weight_for_amount_kg / 1000) * price_per_ton
   ```
   Округление: см. **§4** (в коде пока `.quantize(Decimal("0.01"))` без явного `rounding=`).

4. Если **цена = 0** или **вес для суммы = 0** — в `amount` остаётся то, что распарсили из сообщения (или `0`, если суммы в тексте не было).

**Риск (аудит):** число «Сумма» из весовой может **не совпадать** с тем, что попадёт в `WeighingData.amount` и в PDF, **без отдельного поля** «сумма как в сообщении».

## 2. НДС («В том числе НДС») — правило из `report/pdf_builder.py`

**Файл:** `report/pdf_builder.py` (блок итоговой таблицы, ~стр. 327–331).

**База для расчёта:** `total = calculation_result.total`  
(в пайплайне бота сейчас передаётся `CalculationResult(total=data.amount, ...)`, т.е. фактически **та же сумма**, что уже прошла через правила парсера из §1).

**Формула (как в коде):**

```text
nds_amount = (total / 116) * 16
```

Округление: см. **§4** (в коде — как у суммы, без явного `rounding=`).

**Интерпретация:** сумма считается **с НДС 16% в составе 116%** (выделение НДС из суммы с налогом):  
\(\text{НДС} = \text{итого} \times 16 / 116\).

**Риск:** логика налога живёт в **модуле верстки PDF**, а не в доменном слое; смена источника `total` или формулы потребует правок PDF и может разъехаться с бухгалтерией, если не зафиксировано договором.

## 3. Нетто и брутто в строке товара (PDF) — `report/pdf_builder.py` → `_build_items_table`

**Файл:** `report/pdf_builder.py`, функция `_build_items_table` (переменные `netto_kg`, `brutto_kg` перед добавлением строки в таблицу).

Данные берутся из **`WeighingData`** после парсера.

### 3.1. Нетто для отображения в колонке «Нетто»

```text
netto_display_kg = adjusted_netto_kg or netto_kg
```

- Если **`adjusted_netto_kg` истинно** (в коде сейчас это ненулевое целое; при `0` считается «нет корректировки») — в PDF показывается **вес с корректировкой**.
- Иначе — **`netto_kg`** из сообщения.

### 3.2. Брутто для отображения в колонке «Брутто»

```text
если adjusted_netto_kg истинно:
    brutto_display_kg = tara_kg + adjusted_netto_kg
иначе:
    brutto_display_kg = brutto_kg   # из сообщения
```

### 3.3. Тара

В таблицу выводится **`tara_kg`** из сообщения (перевод в тонны для ячейки).

### 3.4. Риски (аудит)

- Поле **`Брутто`** из сообщения при наличии корректировки **не показывается** — показывается пересчёт **тара + корректировка**, без сравнения с исходным брутто и без предупреждения.
- **`adjusted_netto_kg = 0`** нельзя отличить от «поля не было» — та же проблема truthiness, что в §1.

## 4. Округление денежных сумм и НДС (политика, шаг 011)

**Точность:** все суммы в тенге в документе и расчётах — **до 2 знаков после запятой** (тиыны).

**Режим округления (целевая политика проекта):**

- Использовать **`decimal.ROUND_HALF_UP`** при приведении к `0.01` для:
  - суммы по строке накладной (пересчёт из веса × цена);
  - строки «Итого»;
  - суммы **НДС** после формулы \(×16/116\).

**Обоснование:** половина вверх к ближайшему тиыну — привычная договорённость для коммерческих сумм; при иной норме (банковское `ROUND_HALF_EVEN` и т.д.) этот параграф заменить ссылкой на регламент/договор.

**Текущее состояние кода:** в `parser/parser.py` и `report/pdf_builder.py` вызывается `.quantize(Decimal("0.01"))` **без** аргумента `rounding=...`, т.е. используется **контекст по умолчанию** (`decimal.getcontext()`). Для полного соответствия §4 нужно явно передавать `rounding=ROUND_HALF_UP` (отдельные шаги рефакторинга).

## 5. Политика конфликта `amount_raw` vs `amount_calc` (шаг 012)

### 5.1. Определения

- **`amount_raw`**: сумма из сообщения весовой (как написал оператор / как пришло от системы).
- **`amount_calc`**: сумма по формуле \((\text{вес в кг}/1000)\times\text{цена за тонну}\) с округлением по §4.
- **`amount_final`**: сумма, которая печатается в PDF и попадает в caption.

### 5.2. Порог расхождения

- Определяем \(\Delta = |amount_raw - amount_calc|\).
- Порог незначимого расхождения: **`T = 1.00` тенге** (по умолчанию, пока не согласовано иначе).

### 5.3. Правило выбора `amount_final`

1) Если **цены нет** или **веса нет**, то `amount_calc` не вычисляется →  
   - `amount_final = amount_raw`, источник: `raw`.

2) Если `amount_raw` **отсутствует** в сообщении (пусто/0 как маркер отсутствия в текущей модели) и `amount_calc` вычислилась →  
   - `amount_final = amount_calc`, источник: `calc`.

3) Если `amount_raw` есть и `amount_calc` вычислилась:
   - если \(\Delta \le T\):  
     - `amount_final = amount_raw` (считаем, что это «одно и то же»), источник: `raw`, предупреждений нет;
   - если \(\Delta > T\):  
     - `amount_final = amount_calc`, источник: `calc`;  
     - добавить предупреждение в `warnings`: **«Сумма пересчитана по весу/цене, т.к. сумма в сообщении отличается»**;  
     - логировать warning с `amount_raw`, `amount_calc`, `delta`, `weighing_number`, `invoice_number`.

### 5.4. Зачем это правило

- Убирает «молчаливую подмену» суммы: конфликт становится наблюдаемым (warning + metadata).
- Даёт детерминированность: в одинаковых данных — одинаковый документ.
- Позволяет формализовать и тестировать доменную логику в `invoice_rules`.
